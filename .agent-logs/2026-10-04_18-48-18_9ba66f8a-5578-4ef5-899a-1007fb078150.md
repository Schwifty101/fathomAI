**Section 1: data model and access rules**

The schema is plain Postgres in Supabase.

| Table | Key columns | Notes |
|---|---|---|
| `meetings` | title, kind, platform, started_at, duration_sec | `kind` is e.g. sales call, standup, 1:1, all-hands |
| `participants` | meeting_id, name, role, talk_time_sec | The 8-person call has 8 rows |
| `segments` | meeting_id, participant_id, start_ms, end_ms, text, `tsv` | `tsv` is a generated tsvector with a GIN index. This powers search and the transcript. |
| `chapters` | meeting_id, start_ms, title | Auto-generated at seed time |
| `summaries` | meeting_id, template, content jsonb, `user_id` nullable, source (`seed` or `live`) | `user_id` is null for seeded rows |
| `action_items` | meeting_id, owner, task, due, start_ms | `start_ms` is the moment in the transcript it came from |
| `highlights` | meeting_id, user_id, start_ms, end_ms, note | Private to the user |
| `shares` | slug, meeting_id, start_ms, end_ms, created_by | Public clip links |
| `calendar_events` | title, starts_at, platform | Seeded, powers the calendar stub |

**Access rules (RLS)**
- **Seeded content** (`meetings`, `participants`, `segments`, `chapters`, `summaries`, `action_items`, `calendar_events`) is readable by everyone, including signed-out visitors. Clients can't write to these tables. Only the seed script and my server routes can, using the service role.
- **`highlights`:** each user can read and write only their own rows.
- **`shares`:**
  - Signed-in users can create them.
  - Anyone can open a clip through a security-definer function `get_clip(slug)`.
  - That function returns only the clip window and the meeting title, never the full transcript.
- **Live regeneration** writes a `summaries` row with the caller's `user_id`. The page prefers the caller's own version over the seeded one. A stranger regenerating a summary therefore can't overwrite what other visitors see.
- **Search** is an `rpc` over `segments.tsv` that uses `ts_headline` for snippets and returns meeting, speaker and timestamp, so a result links straight to that moment.

I left out action-item completion state and per-user settings. They're cheap to add later and don't support the core demo.

**Section 2: seed pipeline**

The generator runs on my machine and is never part of the deployed app. It writes JSON files that are committed to the repo. A separate loader pushes them to Supabase.

**Generation (`seed:gen`, uses `claude -p`)**
1. **Brief:** per meeting, one call produces the cast (fictional people and company, 8 speakers for the showcase), the agenda, and 6–8 chapters with the beats each should cover.
2. **Transcript:** one call per chapter, so quality holds over an hour. Each call gets the brief plus the last ~15 lines of the previous chapter. It returns `{speaker, text}` lines only.
3. **Timestamps are stamped in code, not by the model.**
   - They come from word count at about 2.5 words per second, with jitter, small gaps and the occasional overlap.
   - LLM-authored timestamps drift and contradict themselves.
   - The showcase lands around 60–64 minutes.
4. **Summaries and action items:**
   - One call per template over the full transcript, for **General, Sales, Standup and Project review**, so the template switcher always works.
   - Action items return a **segment index**, which code maps to `start_ms`, so the model can't hallucinate a moment that doesn't exist.
   - Relative due dates ("Thursday") are resolved in code against the meeting date. That's the mistake the earlier test call made.
5. **Chapters:** each chapter's start is the first segment of that chapter.

**Content set:** about 7 meetings, all synthetic.
- The 8-person, 62-minute product planning showcase.
- A sales discovery call.
- A daily standup.
- A 1:1.
- A customer interview.
- An incident postmortem.
- A design review.

Dates are spread over the last three weeks.

**Reproducibility:** generation is resumable and skips files that already exist, so a failed run costs only the missing pieces. The model is configurable and defaults to Sonnet.

**Checks (`seed:check`, one script):**
- Output matches the schema (zod). Code fences are stripped, with one retry on bad JSON.
- Every speaker belongs to the cast, and timestamps increase monotonically.
- Showcase duration is within 5% of target, and each of the 8 speakers has meaningful talk time.
- Every action item and chapter anchor resolves to a real segment, and no relative dates are left unresolved.

**Loader (`seed:load`):**
- Uses the service role.
- Uses stable UUIDs derived from each slug, so it's idempotent.
- Upserts everything and recomputes `talk_time_sec` from the segments.

**One call on staleness:** `calendar_events` are stored as an offset from today and resolved at read time. The upcoming-meetings list therefore never shows past dates, even weeks after the seed.

| Route | Purpose |
|---|---|

| `/meetings/[id]` | The core page, described below. It honors `?t=<ms>` to deep-link to a moment. |
| `/search?q=` | Results grouped by meeting, each with a snippet, speaker and timestamp that link to `?t=` |
| `/calendar` | Stubbed "Connect Google Calendar" plus seeded upcoming events |
| `/clip/[slug]` | Public clip page (Section 4) |
| `/auth/callback` | OAuth return |

**Meeting page**
- **Player:**
  - A simulated, clock-driven scrubber with play/pause, 1×/1.5×/2× speed and ±15s skip.
  - It shows per-speaker lanes, chapter markers and highlight markers.
  - The transcript sits beside it on desktop. On mobile the player stacks on top and the tabs sit below.
- **Playback state:** a single `usePlayback` hook runs a `requestAnimationFrame` clock. The active segment comes from a binary search over `start_ms`, so only the active row re-renders and the full list doesn't re-render every frame.
- **Transcript:**
  - All ~1,000 lines of the showcase render in plain DOM with `content-visibility: auto`.
  - Click a line to seek. It auto-follows playback, with a "jump to live" button after a manual scroll.

**Section 4: highlights, sharing, auth, errors, testing and sequencing**

**Highlights**
- **Creating one:** press `H` or tap Highlight during playback. It captures about 5s before to 10s after the playhead, snapped to segment boundaries. An inline note is optional, the insert is optimistic, and a server action writes it under RLS.

**Sharing**
- **Creating a link:**
  - Share from a highlight, from the current moment, or from selected transcript lines.
  - A server action inserts a `shares` row with a 10-character random slug and copies the URL.
